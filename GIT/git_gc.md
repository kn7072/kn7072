# Настройка Git Garbage Collection (gc) для системы бэкапов в Neovim

В этой документации подробно разбираются все настройки `git gc`, которые используются в кастомной системе бэкапов через Git-репозиторий.

## 📚 Основные понятия

Прежде чем разбирать настройки, важно понять, как Git хранит данные:

| Термин           | Описание                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------- |
| **Loose object** | Рыхлый объект — каждый коммит, файл или дерево хранится как отдельный сжатый файл.       |
| **Pack file**    | Упакованный файл — множество объектов, сжатых вместе в один файл (экономит место).       |
| **Reflog**       | Журнал ссылок — история перемещений веток и HEAD (ваш "журнал отмен" в Git).             |
| **Reachable**    | Достижимый объект — можно найти, пройдя от текущей ветки по ссылкам.                     |
| **Unreachable**  | Недостижимый объект — нельзя найти от текущей ветки (старые версии, изменённые коммиты). |

---

## ⚙️ Подробное описание каждой настройки

### 1. `gc.reflogExpire = "30 days"`

**Что контролирует**: Время жизни **достижимых** записей в reflog.

**Схема работы**:

```
[Ваша ветка main] → [Коммит A] → [Коммит B] → [Коммит C (текущий)]
                    ↑                           ↑
               достижимый                   достижимый
```

**Как работает**:

- Reflog хранит историю перемещений указателя ветки.
- Через 30 дней после того, как запись стала достижимой из текущего состояния, она может быть удалена.
- Пример: вы сделали коммит сегодня → он достижим → будет удалён через 30 дней.

**Для вашей системы бэкапов**:

- Каждое сохранение создаёт новый коммит в ветке.
- Все коммиты старше 30 дней будут удалены при `git gc`.
- **Итог**: вы можете восстановить файлы, изменённые не позже 30 дней назад.

---

### 2. `gc.reflogExpireUnreachable = "7 days"`

**Что контролирует**: Время жизни **недостижимых** записей в reflog.

**Схема работы**:

```
Исходная история:
[Коммит 1] → [Коммит 2] → [Коммит 3 (текущий)]
                          ↑
                     достижимый

После git commit --amend (переписали историю):
[Коммит 1] → [Коммит 2] → [Коммит 3NEW (текущий)]
                             ↑
                        достижимый
[Коммит 3OLD] ← недостижимый (удалится через 7 дней)
```

**Как работает**:

- Недостижимые объекты появляются при: `git commit --amend`, `git rebase`, `git reset --hard`.
- Через 7 дней после создания они становятся кандидатами на удаление.

**Для вашей системы бэкапов**:

- Если вы перезаписываете историю, старые версии файлов становятся недостижимыми.
- Они будут храниться **7 дней**, потом удалятся.
- **Итог**: у вас есть неделя, чтобы передумать после перезаписи истории.

---

### 3. `gc.pruneExpire = "14 days"`

**Что контролирует**: Через сколько времени удаляются **физические файлы** недостижимых объектов после того, как они исчезли из reflog.

**Таймлайн жизни недостижимого коммита**:

```
Таймлайн жизни недостижимого коммита:

День 0: Создан коммит (стал недостижимым)
   ↓
День 7: Запись в reflog истекла (gc.reflogExpireUnreachable)
   ↓
День 14: Физический файл удалён (gc.pruneExpire)
   ↓
День 15: Объекта больше нет в репозитории
```

**Как работает**:

- Это «период ожидания» перед окончательным удалением.
- Защита от случайного удаления объектов, на которые всё ещё могут быть ссылки.

**Для вашей системы бэкапов**:

- Недостижимые версии файлов живут минимум 7 дней (reflog) + максимум 14 дней (prune) = до 21 дня.
- **Итог**: даже после перезаписи истории у вас есть 2-3 недели на восстановление.

---

### 4. `gc.auto = 500`

**Что контролирует**: Количество **рыхлых объектов** (loose objects), при превышении которого автоматически запускается `git gc --auto`.

**Как работает**:

- Каждый новый объект сначала создаётся как «рыхлый» (отдельный файл).
- Когда число рыхлых объектов превышает `gc.auto`, запускается `git gc --auto`.
- Значение `0` отключает автоматический запуск.

**Расчёт**:

```
Значение по умолчанию: 6700 объектов
Ваше значение: 500 объектов

Почему 500? При частых сохранениях (каждые 5-10 секунд) вы быстро набираете 6700 объектов (через ~10-20 часов непрерывной работы). 500 объектов — это ~30-60 минут работы, очистка будет происходить чаще, но репозиторий будет компактнее.
```

**Для вашей системы бэкапов**:

- Каждое сохранение создаёт новый рыхлый объект (коммит).
- При достижении 500 коммитов без упаковки запустится `git gc`.
- **Итог**: репозиторий будет упаковываться примерно каждые 500 сохранений.

---

### 5. `gc.autoPackLimit = 30`

**Что контролирует**: Максимальное количество **pack-файлов** перед принудительной упаковкой.

**Как работает**:

- Со временем создаётся несколько pack-файлов (каждый результат `git gc --auto`).
- Когда их количество превышает `gc.autoPackLimit`, Git запускает более агрессивную упаковку и объединяет все pack-файлы в один.

**Значения**:

- Значение по умолчанию: 50.
- Ваше значение: 30.

**Для вашей системы бэкапов**:

- При превышении 30 pack-файлов запускается `git gc --auto`.
- Git объединяет все pack-файлы в один, удаляя дубликаты.
- **Итог**: репозиторий остаётся хорошо сжатым, не раздувается.

---

## 🔄 Как эти настройки взаимодействуют

Вот пошаговый сценарий работы автоматической очистки в вашей системе:

1.  **Пользователь делает `:w`** (сохраняет файл).
2.  Создаётся новый коммит (рыхлый объект).
3.  **Число рыхлых объектов растёт.**
4.  **Превышен `gc.auto = 500`?**
    - **ДА** → Запускается `git gc --auto`.
    - **НЕТ** → Возврат к шагу 1.
5.  **`git gc --auto` выполняет очистку:**
    - Удаляет записи в reflog старше 30 дней (достижимые).
    - Удаляет записи в reflog старше 7 дней (недостижимые).
    - Удаляет файлы объектов старше 14 дней (prune).
6.  **Проверить число pack-файлов > 30?**
    - **ДА** → Выполнить полную упаковку (объединить все pack-файлы).
    - **НЕТ** → Завершить.
7.  **Репозиторий очищен и оптимизирован.**

## 💡 Советы по настройке под ваши нужды

Вы можете изменить эти параметры в зависимости от ваших приоритетов:

**Если вы хотите хранить историю дольше:**

```bash
git config gc.reflogExpire "90 days"  # вместо 30
git config gc.pruneExpire "30 days"    # вместо 14

```

## Если репозиторий слишком быстро растёт (нужно чаще чистить):

```bash
git config gc.auto "200"   # чаще упаковывать
git config gc.autoPackLimit "20"  # агрессивнее сжимать
```

## Если важна производительность (меньше фоновой работы):

```bash
git config gc.auto "2000"  # реже запускать gc
```
